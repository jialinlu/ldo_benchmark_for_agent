# EvoLDO-Bench 模拟设计专家独立审题指南

> 本文用于转交模拟 IC/LDO 设计专家。目标不是请专家替项目“背书”，而是系统性发现题目、
> 物理逻辑、测试维度、评分规则和晶体管级闭环任务中的错误与盲区。

## 0. 审阅任务与预期交付

烦请专家以模拟设计工程经验独立完成以下交付：

1. 按第 6 节模板记录具体问题、严重度、证据和修改建议；
2. 按第 7 节评价整体能力覆盖、工程真实性、区分度和防投机能力；
3. 对第 4.5 节的测试维度给出“v1 必须/后续应加/不适合纳入/需要重新定义”的优先级；
4. 明确给出“可用、修改后可用、仅适合作为示例或不建议使用”的最终结论；
5. 如条件允许，复跑六个 SKY130 任务并附上无法复现或阈值不合理的证据。

不要求专家修改代码，也不要求为了给出意见而接受现有设计。指出题目无法唯一作答、指标不值得
测量或整个任务方向不合理，同样是有效且重要的评审结果。

## 1. 为什么需要专家审题

EvoLDO-Bench 希望判断 AI 是否真正具备 LDO 分析、诊断、设计和闭环能力，而不是只会复述模拟
电路术语。自动测试能够检查文件、哈希、格式和数值，却无法独立证明以下事项：

- 题目的物理前提是否成立，是否存在多个同样合理的答案；
- canonical、metamorphic、counterexample 三类变体是否真的保持或改变了应有的物理事实；
- 所谓“致命错误”是否确实应该封顶，推荐动作是否符合工程实践；
- testbench、激励、测量表达式和阈值是否测到了声称要测的能力；
- 任务是否可以通过投机、修改测试平台或使用非物理器件绕过；
- 当前测试维度是否足以支撑“LDO 设计能力”这一结论。

因此，正式考试发布前应由**两位模拟设计工程师独立审阅**，再对分歧进行统一裁决。两位专家的
结论一致并不自动代表题目正确；存在分歧也不代表某位专家错误，分歧往往暴露了题意不唯一或
测试边界没有写清楚。

## 2. 当前 benchmark 概况

当前公开开发集由两部分组成：

1. **LDO 推理任务：40 个 family / 120 个 instance**
   每个 family 包含 canonical、metamorphic 和 counterexample，覆盖结构识别、趋势、故障诊断、
   sizing、工艺迁移、系统影响、设计闭环和架构选择。
2. **SKY130 晶体管级闭环任务：6 个**
   覆盖标称工作点与静态电流、真实冷启动、关断/重启、负载瞬态、线性/负载调整率和 PVT/器件
   合规检查。每个 starter 均注入一个受控故障，必须修改 DUT 并取得新的 ngspice 仿真证据。

当前集合是公开 development track，不是密封考试，也不代表流片或产品性能。专家需要同时审阅
“我们是否正确测量了声明的能力”和“当前能力声明是否过大”。

## 3. 建议的双专家审阅方式

### 3.1 独立性要求

- 专家 A、专家 B 在提交第一轮意见前不要相互讨论结论。
- 第一轮先看题目和输入，**不要先看 oracle、参考答案或参考候选**；独立写出预期结论和理由。
- 第二轮再查看 oracle、评分项、参考候选和仿真证据，检查它们是否正确且是否过拟合。
- 两份原始意见应保留，不要在会前合并或覆盖。
- 分歧会议只处理已经记录的问题；裁决结论、修改决定和不采纳理由均需留档。

### 3.2 推荐工作量

| 审阅档位 | 内容 | 预计时间 | 能否作为正式签核 |
|---|---|---:|---|
| 框架评审 | 阅读总体方法、能力矩阵、评分方式和 6 个闭环任务摘要 | 1–1.5 小时 | 否 |
| 核心深审 | 两位专家均审 6 个闭环任务及高风险 numeric/closure families | 3–5 小时/人 | 可作为阶段签核 |
| 全量签核 | 两位专家检查全部 family；numeric/closure 必须双人独立深审 | 1–2 个工作日/人 | 是 |

如果时间有限，可以先做核心深审，但报告中必须写明未审范围，不能将抽样评审描述成全量签核。

### 3.3 两轮审阅

**第一轮：盲审物理问题**

1. 题目是否自洽、信息是否足够；
2. 专家自己的结论、证据链、关键假设和允许的备选答案；
3. 哪些条件一变，结论就应该变化；
4. 题目实际上测的是哪种能力，有没有只靠关键词就能答对。

**第二轮：审 oracle、grader 和仿真闭环**

1. oracle 是否与独立结论一致；
2. 评分项是否遗漏合理答案或错误奖励伪因果；
3. critical cap 是否只用于真正致命的结论；
4. 参考候选能否通过，故障 starter 是否应当失败；
5. 仿真证据、模型版本、corner、温度、负载和测量表达式是否完整绑定。

## 4. 必须审阅的五个层次

### 4.1 Benchmark 总体逻辑

请判断：

- “结构 → 趋势 → 诊断 → sizing → 闭环”的能力分层是否合理；
- 40 个 family 是否存在明显重复、能力空洞或难度失衡；
- family macro score 是否能避免大量简单题淹没少量关键题；
- Pass@1、spec score、关键错误封顶和 score-versus-effort 是否足以反映工程能力；
- direct、skill、simulation 三种 treatment 的对照是否真的只改变了目标变量；
- 是否存在 prompt 长度、固定术语、答案格式或任务 ID 泄露答案的捷径。

### 4.2 Family 与三类变体

对每个 family 检查：

- canonical 是否代表一个真实且常见的设计/调试问题；
- metamorphic 是否仅改变名字、顺序、层级或表达形式，而没有偷偷改变物理条件；
- counterexample 是否只改变一个关键事实，并且足以改变正确结论；
- 三个变体是否共享正确的 lineage，是否会因为记住答案模板而免费得分；
- held-fixed 条件是否完整，趋势题是否把多变量变化误写成单变量因果；
- 是否存在两个以上同样合理但 grader 只接受一个的答案。

### 4.3 Oracle、评分项与关键错误

请重点检查：

- `conclusion`、`evidence`、`mechanism`、`action` 是否互相一致；
- 推荐修复动作是否可能破坏 headroom、IQ、噪声、稳定性或启动等其他维度；
- forbidden action 是否真的不应执行，还是只在某些 operating regime 下不合适；
- 权重是否与工程风险匹配；
- critical 项是否满足“结论错误会导致方向性错误或不安全设计”的标准；
- 数值容差是否考虑仿真器、模型版本和采样误差，同时又不会宽到失去区分度。

### 4.4 六个 SKY130 晶体管级闭环任务

每个任务必须逐项检查：

1. **DUT 与架构**：反馈方向、body 连接、偏置和 EN 极性是否正确；参考设计是否依赖隐藏理想条件。
2. **故障注入**：starter 是否主要包含一个故障；该故障是否必然触发目标失败；是否存在无关副作用。
3. **Testbench**：激励边沿、负载、输入输出范围、仿真时长和初始状态是否符合目标场景。
4. **Measurement**：测量窗口是否避开错误的瞬态阶段；电流符号、crossing 次数和单位是否正确。
5. **Threshold**：上下限是否有物理和工程依据；是否过松、过严或只为让参考候选通过。
6. **防投机**：能否通过在候选中加入顶层源、隐藏 include、`.ic`、`.nodeset` 或修改 bench 绕过。
7. **失败分类**：模型/仿真器失败是否保持为 `INFRA_FAIL`；未达到阈值是否正确归为电路失败；测量缺失是否会被误判。
8. **证据新鲜度**：candidate、deck、log 是否绑定；修改候选后能否错误继承旧结果。

请特别判断当前 1.8 V 输入、约 1.5 V 输出、0.1–1 mA 负载、10 pF 负载电容的开发规格，是否
足以暴露有意义的 LDO 设计差异，还是过于简单、过于依赖某一参考架构。

### 4.5 测试维度完整性

请对下列维度标注“v1 必须 / 后续应加 / 不适合纳入 / 需要重新定义”，并说明理由：

| 维度 | 当前覆盖 | 请专家判断 |
|---|---|---|
| DC 工作点、反馈精度、IQ | 已覆盖 | 阈值和负载点是否合理 |
| 冷启动、关断、重启 | 已覆盖 | 是否需不同 ramp、EN slew、带载启动 |
| 负载瞬态 | 已覆盖 | 是否需更多边沿、CLOAD、ESR 和负载范围 |
| 线性/负载调整率 | 初步覆盖 | 是否应加入 dropout sweep 和 line transient |
| PVT | 初步覆盖 | 是否需 FS/SF、更多温度/电压组合 |
| 环路稳定性 | 仅有瞬态侧面约束 | 是否必须加入 return-ratio/STB 类硬门槛 |
| PSRR | 推理题覆盖，晶体管闭环未覆盖 | 频点、注入方式和工作点应如何定义 |
| 噪声 | 推理题覆盖，晶体管闭环未覆盖 | 积分带宽、reference noise 是否应纳入 |
| current limit/短路保护 | 未覆盖 | 是否属于基础 LDO 能力还是进阶任务 |
| mismatch/Monte Carlo | 未覆盖 | public benchmark 是否需要统计良率门槛 |
| 反向电流、掉电顺序 | 未覆盖 | 是否应作为鲁棒性/保护类任务 |
| 面积、器件应力、可靠性 | 未覆盖 | 前端任务应检查到什么程度 |

这一部分非常重要：专家可以明确建议**删除**不适合作为通用 benchmark 的维度，而不是默认维度
越多越好。

## 5. 建议专家重点回答的问题

### 5.1 大方向问题

1. 当前 benchmark 测到的是“LDO 专项能力”，还是通用问答和格式遵循能力？
2. 哪三类能力最能区分会说术语的模型与真正能推进设计闭环的 agent？
3. 当前能力矩阵中最大的缺口是什么？哪些已有维度价值较低或高度重复？
4. 公开开发集与未来密封考试之间，哪些内容必须保持隐藏才有可信度？
5. 如果只保留 10–15 个高价值 family，您会保留哪些，为什么？

### 5.2 工程细节问题

1. 目前故障注入是否符合工程师实际遇到的失败模式？
2. 是否存在看似合理但会导致错误修复方向的 oracle/action？
3. 当前 transient 规格能否替代稳定性硬门槛；如果不能，推荐怎样建立开源 ngspice 可复现的稳定性测试？
4. PSRR、噪声、dropout、current limit、Monte Carlo 中，v1 最应优先补哪两项？
5. 哪些规格应该是 eligibility hard gate，哪些适合进入连续性能评分？
6. 是否应提供多个架构和多个负载等级，避免 agent 只学会修一个小电流 PMOS LDO？
7. 当前禁止理想源的策略是否合理；理想 passive、testbench source 和 DUT 内辅助模型的边界应如何定义？
8. 对弱 agent 来说，任务给出的信息是否足够；增加信息会帮助设计还是泄露解题路径？

严重度定义：

- **P0 致命**：正确答案错误、反馈方向错误、bench 测错对象、存在直接作弊通道，任务不得发布；
- **P1 重要**：题意不唯一、关键 corner/条件缺失、阈值缺乏依据，会显著影响模型排序；
- **P2 一般**：表述、容差或次要评分不合理，但不改变主要结论；
- **P3 建议**：可读性、扩展方向或非阻塞优化。

## 8. 裁决与签核规则

建议采用以下门槛，而不是简单要求“两位专家都说可以”：

1. 所有 P0 必须关闭；P1 必须关闭或由裁决记录明确接受风险。
2. numeric 和晶体管级 closure 任务必须有双人独立结论；不能用抽样代替。
3. 对正确结论、critical error、measurement 和 threshold 的分歧必须逐项裁决。
4. family 的正确答案若依赖未写出的假设，应重写任务，而不是只在 oracle 中补充解释。
5. 修改物理结论、bench、阈值或 critical cap 后，原签核失效，相关任务需重新审阅。
6. 正式发布记录应保留专家原始意见、裁决结论、修改 commit 和复测证据。

如两位专家对关键物理结论仍无法达成一致，建议引入第三位专家裁决，或者删除该题。一个需要
依靠维护者口头解释才能成立的题目，不适合作为自动化 benchmark。

仿真复核时请记录操作系统、ngspice 版本、模型入口 SHA-256、candidate SHA-256 和产生结果的 commit。

## 10. 保密与材料边界

本轮只评审公开 benchmark 内容。请不要在意见中加入公司内部 PDK 名称、模型路径、服务器信息、
内部 testbench、未公开电路、账号或许可证信息。如果需要用内部经验解释问题，请抽象成不带公司
标识的物理描述；确实无法公开的证据应单独通过受控渠道保存，不进入公开仓库。
